# Yandex Live Subtitles Translator: техническое описание

## Назначение

Yandex Live Subtitles Translator - локальная система для перевода live-субтитров Яндекс Браузера в реальном времени.

Система не использует платные облачные API. Перевод выполняется локально через Ollama или другой локальный backend. Основной сценарий - технические трансляции: Google I/O, Apple WWDC, Microsoft Build, OpenAI DevDay, продуктовые презентации и developer keynotes.

Основной поток данных:

```text
Видео в Яндекс Браузере
  -> live-субтитры Яндекс Браузера
  -> чтение текста через extension / CDP reader
  -> локальный translator-server
  -> Ollama model
  -> RU subtitle overlay в браузере или отдельная HTML-страница для vMix
```

## Почему берем субтитры у Яндекса

Самая дорогая и рискованная часть такой системы - распознавание речи. Если делать собственный ASR, придется отдельно решать:

- захват аудио из вкладки или системного микса;
- разделение речи, музыки и пауз;
- realtime VAD;
- ASR-модель;
- пунктуацию;
- восстановление грязной транскрипции;
- задержку между речью и переводом;
- нагрузку на ПК, где параллельно может работать vMix.

Яндекс Браузер уже делает live ASR и показывает английские субтитры. Поэтому текущий проект использует Яндекс как источник английского текста, а не как переводчик.

Плюсы подхода:

- меньше нагрузка на ПК;
- меньше задержка, чем при полном собственном ASR pipeline;
- проще добиться стабильности;
- можно сосредоточиться на качестве EN -> RU перевода и отображении.

Минусы:

- зависимость от DOM/внутренней реализации Яндекс Браузера;
- если Яндекс не показывает live-субтитры на конкретном сайте или трансляции, системе нечего читать;
- ошибки ASR Яндекса попадают в переводчик;
- closed shadow DOM требует обходных механизмов.

## Почему не подменяем Яндекс-виджет

Перевод не вставляется внутрь оригинального блока Яндекс Браузера. Вместо этого система рисует собственный overlay.

Причины:

- Яндекс-виджет живет внутри web components и shadow DOM;
- часть shadow root может быть closed;
- прямое вмешательство в внутреннюю верстку браузерного виджета нестабильно;
- Яндекс может менять DOM без предупреждения;
- отдельный overlay проще контролировать: размер, позицию, прозрачность, две строки, скрытие при паузе;
- тот же текст можно отдавать в отдельную HTML-страницу для vMix.

В итоге оригинальные английские субтитры остаются источником данных, а русский перевод выводится отдельно:

- overlay поверх видео в браузере;
- `/overlay` HTML-страница от локального backend для vMix/browser source.

## Основные компоненты

### Browser extension

Папка:

```text
extension/
```

Задачи расширения:

- запускаться на `document_start`;
- внедрять `injected.js` в MAIN world;
- пытаться перехватить `Element.prototype.attachShadow`;
- читать субтитры из DOM/shadow DOM, если доступ есть;
- использовать CDP fallback, если shadow root уже закрыт;
- стабилизировать поток английского текста;
- не отправлять каждое новое слово в переводчик;
- фильтровать дубли и короткие обрывки;
- отправлять EN-текст в `translator-server`;
- показывать RU-текст в overlay;
- показывать debug panel при включенном debug mode.

### Injected script

Файл:

```text
extension/src/injected.js
```

Он выполняется в MAIN world страницы. Это важно, потому что content scripts Chrome/Chromium по умолчанию работают в isolated world, а перехват `attachShadow` из isolated world не влияет на страницу.

Идея:

- сохранить оригинальный `Element.prototype.attachShadow`;
- если shadow root создается для `ya-asr-subtitles-widget`, попытаться создать его как `open`;
- отправить событие о доступности shadow root;
- не ломать остальные web components.

Ограничение:

Если closed shadow root уже создан до запуска extension, открыть его позже нельзя. Поэтому используется CDP fallback.

### CDP reader

Папка:

```text
subtitle-cdp-reader/
```

CDP reader подключается к Яндекс Браузеру через remote debugging port. Он выполняет JavaScript в контексте вкладки и читает live-субтитры там, где extension уже не может достать closed shadow root напрямую.

Сценарий:

```text
Yandex Browser --remote-debugging-port=9222
  -> subtitle-cdp-reader на 127.0.0.1:8766
  -> GET /subtitles
  -> extension получает EN text
```

Именно поэтому браузер желательно запускать через `run_all_servers.bat`: он стартует Яндекс с нужным debug port.

### Translator server

Папка:

```text
translator-server/
```

FastAPI backend слушает только `127.0.0.1`.

Основные endpoints:

- `GET /health` - состояние сервера и выбранного backend;
- `POST /translate` - перевод EN -> RU;
- `POST /subtitle` - публикация текущего перевода для внешнего overlay;
- `GET /current` - текущий subtitle state;
- `GET /overlay` - HTML-overlay для vMix/browser source.

Backend делает:

- нормализацию пробелов;
- ограничение длины входа;
- LRU cache;
- ограничение очереди;
- один активный перевод;
- timeout;
- логирование в отдельный файл `logs/translations_YYYYMMDD_HHMMSS.jsonl` для каждого запуска;
- сохранение короткой истории контекста для модели.

## Как работает перевод

Extension отправляет запрос:

```json
{
  "text": "And I'm excited to introduce Gemini Intelligence.",
  "source_lang": "en",
  "target_lang": "ru",
  "model": "translategemma:12b",
  "profile": "tech_keynote"
}
```

Backend:

1. Нормализует текст.
2. Проверяет cache.
3. Применяет ASR corrections из glossary.
4. Выбирает prompt/profile.
5. Отправляет запрос в Ollama.
6. Чистит ответ модели.
7. Логирует latency и результат.
8. Возвращает перевод extension.

Пример ответа:

```json
{
  "translation": "И я рад представить Gemini Intelligence.",
  "backend": "ollama",
  "model": "translategemma:12b",
  "cached": false,
  "latency_ms": 1227
}
```

## Стабилизация live-текста

Live-субтитры приходят не готовыми предложениями, а меняющимися окнами текста:

```text
After
After the
After the games
After the games today, just one more
```

Если переводить каждое состояние, будет много мусора, дублей и рывков. Поэтому extension делает промежуточную стабилизацию:

- ждет небольшую паузу;
- быстрее выпускает фразы с нормальной пунктуацией;
- удерживает подозрительные короткие обрывки;
- склеивает продолжения;
- отбрасывает повторные фразы;
- не держит длинную очередь;
- важнее актуальный перевод, чем полный архив.

Последние правки добавили:

- защиту от двойного запуска content script;
- память отправленных фраз на 45 секунд;
- подавление повторного показа одинакового RU;
- чистку повторов внутри одной фразы;
- более осторожную обработку коротких хвостов;
- отбрасывание недописанных хвостов при паузе >= 5 секунд (раньше они дотолкивались на overlay);
- настраиваемый порог полного сброса контекста (по умолчанию 15 секунд тишины вместо прежних 30);
- ручную кнопку сброса памяти переводчика в настройках расширения (для сценария «прогрев → реальный эфир»);
- две модели промпта на выбор пользователя: `красивый` (литературный) и `короткий` (близко к длине английского, для overlay);
- фильтр выходного текста: убирает плейсхолдеры `[имя]`, XML-теги `<unk>`, незакрытые кавычки/скобки, осиротевшие английские префиксы в начале русского;
- кэш имён в рамках сессии: одно имя переводится одинаково все время эфира;
- словарь ASR-исправлений и продуктовых имён для типичных тех-кейноутов.

## Overlay

Есть два режима вывода:

1. Overlay прямо поверх видео в браузере.
2. HTML-overlay по адресу `http://127.0.0.1:8765/overlay` для vMix.

Overlay сделан как фиксированная двухстрочная лента:

- максимум 2 видимые строки;
- плавная прокрутка вверх;
- старые строки уходят;
- блок скрывается после паузы;
- pointer-events отключены;
- фон полупрозрачный;
- параметры регулируются в extension settings или через query params HTML-overlay.

## Почему выбран Ollama

Ollama выбран как основной механизм локального запуска LLM:

- простой запуск на Windows;
- модели можно хранить на другом диске;
- не нужен внешний API;
- удобно менять модели;
- есть локальный HTTP API;
- можно держать модель в памяти через `keep_alive`;
- подходит для ПК уровня i7-12700K / 64 GB RAM / RTX 4070 Ti.

## Какие модели тестировались

### qwen2.5:1.5b

Плюсы:

- легкая;
- быстро запускается;
- низкая нагрузка.

Минусы:

- качество перевода слабее;
- хуже держит русский;
- больше буквального и неестественного перевода;
- не подходит как основная модель для технических мероприятий.

Итог: годится как аварийный fallback, но не как основной режим.

### qwen2.5:3b

Плюсы:

- лучше 1.5B;
- приемлемая нагрузка;
- может работать быстро.

Минусы:

- качество перевода нестабильное;
- были артефакты, повторы, странный русский;
- иногда появлялись китайские символы или смешение языков;
- плохо переносит грязные live-фрагменты.

Итог: изначально рассматривалась как основной кандидат, но по качеству не устроила.

### qwen2.5:7b

Плюсы:

- потенциально лучше по смыслу, чем 1.5B/3B;
- лучше понимает контекст.

Минусы:

- тяжелее;
- нежелательна как обязательная модель рядом с vMix;
- все равно не решает полностью проблему live-сегментации.

Итог: можно тестировать, но не выбрана как базовая.

### aya-expanse:8b

Плюсы:

- лучше ориентирована на multilingual translation;
- дала более естественный русский, чем ранние qwen-тесты.

Минусы:

- качество все равно нестабильное на коротких фрагментах;
- не всегда достаточно хорошо держала технический keynote-стиль;
- скорость/качество оказались не лучшим балансом.

Итог: полезный кандидат, но не текущий основной выбор.

### translategemma:12b

Плюсы:

- лучшее качество русского среди протестированных вариантов;
- стабильнее на технических текстах;
- меньше артефактов;
- лучше переносит glossary и профиль `tech_keynote`;
- после прогрева дает хорошую скорость подачи;
- на текущем железе работает приемлемо.

Минусы:

- первые минуты после старта могут быть тяжелее;
- выше нагрузка, чем у 3B/8B моделей;
- при плохой сегментации все равно может переводить кусками;
- требует аккуратной стабилизации входного текста.

Итог: выбрана как основной режим на текущем этапе.

### CTranslate2 / OPUS-MT

Планировался как быстрый fallback:

```text
ct2_opus
```

Плюсы:

- быстрый;
- CPU-friendly;
- предсказуемый;
- полезен, если Ollama мешает рабочей машине.

Минусы:

- качество хуже LLM на презентациях;
- хуже контекст;
- хуже естественность русского;
- меньше гибкости через prompt.

Итог: архитектурно оставлен как fallback, но основной упор сейчас на Ollama + LLM.

## Почему качество зависит не только от модели

Главная проблема live-перевода - не только EN -> RU модель. Проблема в том, что модель часто получает не предложение, а кусок:

```text
It's one seamless Gemini intelligence experience across your phone, your
```

А потом отдельно:

```text
watch, your car, and glasses too.
```

Если вторую строку переводить отдельно, `watch` может стать глаголом `смотрите`, а не устройством `часы`.

Поэтому качество улучшается тремя слоями:

1. Стабилизация и склейка EN-фрагментов.
2. ASR corrections и glossary.
3. Prompt/profile/history для модели.

Модель не может надежно исправить все, если вход уже неправильно разрезан.

## Глоссарий и ASR corrections

Файл:

```text
translator-server/app/glossary/glossary.yaml
```

Он содержит:

- термины, которые лучше оставлять как есть;
- preferred translations;
- исправления частых ASR-ошибок.

Примеры задач glossary:

- `AI Mode` не переводить как случайный "режим искусственного интеллекта", если это продуктовый термин;
- `Veo 3`, `Gemini`, `Jules`, `Google I/O` не коверкать;
- исправлять типовые ASR-ошибки вроде `vo three` -> `Veo 3`, если контекст очевиден.

Глоссарий не должен превращаться в список исключений на каждую фразу. Его задача - стабилизировать повторяющиеся термины и частые ошибки распознавания.

## Прогрев модели

Первые запросы после старта Ollama обычно медленнее:

- модель грузится в память;
- Ollama поднимает runtime;
- GPU/CPU кеши еще холодные;
- первая генерация дороже последующих.

Прогрев можно сделать простым запросом при старте backend:

```text
Translate: "Hello, welcome to the keynote."
```

Цель прогрева - не получить полезный перевод, а заставить модель загрузиться и выполнить короткую генерацию до начала трансляции.

Ожидаемый эффект:

- первые реальные субтитры будут обрабатываться быстрее;
- меньше стартовых зависаний;
- стабильнее latency после открытия трансляции.

Минусы:

- запуск сервера станет немного дольше;
- модель начнет потреблять память сразу после старта;
- если пользователь не собирается переводить прямо сейчас, ресурсы будут заняты заранее.

## Логи и анализ качества

Переводы пишутся в:

```text
logs/translations_YYYYMMDD_HHMMSS.jsonl
```

Каждая строка содержит:

- timestamp;
- EN text;
- RU translation;
- backend;
- model;
- profile;
- cached;
- latency;
- status/error.

По этим логам оцениваются:

- median/p90/p95 latency;
- длинные паузы между выводами;
- повторы;
- короткие обрывки;
- weak endings;
- артефакты модели;
- качество русского;
- терминология.

Важно: автоматические метрики не заменяют ручной просмотр. Они показывают подозрительные места, но качество русского и смысл надо оценивать глазами.

## Текущие ограничения

- Если Яндекс не показывает субтитры, проект не получает исходный EN-текст.
- Если сайт/вкладка не доступны через CDP, fallback не сработает.
- При резких паузах, музыке и перебивках возможны задержки или скрытие overlay.
- При слишком коротких фрагментах модель может ошибаться по смыслу.
- При смене DOM Яндекс Браузера может понадобиться обновление reader.
- Собственный ASR пока не реализован намеренно.

## Почему не собственный ASR сейчас

Собственный ASR технически возможен, но это другой уровень проекта.

Потребуется:

- захват аудио;
- VAD;
- Whisper/faster-whisper или аналог;
- punctuation restoration;
- diarization, если нужно;
- отдельная оптимизация GPU/CPU;
- синхронизация ASR и перевода;
- больше задержка;
- выше нагрузка рядом с vMix.

Текущий подход рациональнее для MVP: использовать готовый ASR Яндекса и улучшать перевод, сегментацию и вывод.

## Как запускать

Полная пошаговая установка и запуск описаны в [README.md](../README.md). Кратко:

| Файл | Что делает |
|---|---|
| `setup_windows.bat` | Первичная установка: venv, зависимости, скачивание модели |
| `run_all_servers.bat` | Запуск всей системы перед эфиром |
| `doctor.bat` | Проверка «всё ли установлено правильно» |
| `cleanup.bat` | Очистка логов, остановка зависших процессов |

Перед эфиром:

1. Открыть Яндекс Браузер, запущенный через launcher.
2. Открыть видео/трансляцию.
3. Включить live-субтитры Яндекс Браузера.
4. Убедиться, что extension включен.
5. Если делали прогрев модели — открыть настройки расширения и нажать **Сбросить память переводчика сейчас**.
6. При необходимости открыть HTML-overlay для vMix: `http://127.0.0.1:8765/overlay`.

## Что развивать дальше

Уже сделано:

- настраиваемые профили `tech_keynote`, `general`, `politics_news`;
- переключаемые стили промпта (`красивый` / `короткий`) через настройки расширения;
- автоматический прогрев модели при старте backend;
- расширенный глоссарий ASR-исправлений и продуктовых имён;
- кэш имён в сессии для стабильности перевода;
- ручной сброс памяти переводчика из настроек расширения.

Полезные улучшения, которые ещё можно сделать:

- логировать причины решений segmenter (`duplicate_skipped`, `fragment_held`, `fragment_joined`);
- улучшить склейку continuation-фрагментов;
- автоматически включать fallback на `ct2_opus` при перегрузке Ollama;
- расширять глоссарий по реальным логам WWDC / Google I/O / Build / DevDay;
- отдельный режим «качество» с большей задержкой и лучшей склейкой;
- отдельный режим «скорость» с меньшей задержкой;
- собственный ASR pipeline (отдельный большой шаг, не приоритет).
